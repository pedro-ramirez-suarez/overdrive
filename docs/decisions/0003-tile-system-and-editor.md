# ADR 0003 — Tile system, connection contract, and editor (M3)

Status: Accepted (M3)

## Context

M3 is the keystone (SPEC.md §5.2, §M3): a grid of snap-together tiles with a
strict socket connection contract, and a minimal editor to place them.

## Decisions

### 1. Data model

- `TileSocket` (Resource): `has_road`, `elevation_level`, `slope {FLAT,UP,DOWN}`.
- `TileDefinition` (Resource): `id`, `display_name`, `footprint`, `mesh`
  (PackedScene), four base sockets `[N,E,S,W]`, `is_stunt`, `category`.
- `PlacedTile` (RefCounted): `def_id`, `rotation` (0-3), `elevation_level`.
- `TrackGrid` (RefCounted): `Vector2i -> PlacedTile`; `place`/`remove`/
  `get_socket`/`cells_connected`. Directions N/E/S/W = 0/1/2/3; grid X→world X,
  grid Y→world Z. `get_socket` applies rotation (`base = (dir - rotation) mod 4`)
  and adds the tile's placed elevation to the socket's base level.

`is_connected` had to be renamed `cells_connected` — `Object.is_connected`
(signals) already exists and GDScript rejects the override.

### 2. Connection rule (exactly as specified)

Two adjacent sockets connect iff both have road, elevation levels are equal, and
slopes are complementary (FLAT↔FLAT or UP↔DOWN). Ramps carry the elevation
change via differing socket levels with FLAT slopes, so they connect cleanly to
flat tiles; UP/DOWN is reserved for ramp-to-ramp joins.

### 3. Definitions built in code, geometry generated procedurally

`TileLibrary` constructs the `TileDefinition`s in code rather than authoring
`.tres` files — the data model is unchanged and this removes hand-authoring risk
(and the typed-socket-array serialization guesswork). Moving them to `.tres` is a
later, mechanical step. Tile meshes are generated by `TileGeo` (same swept-ribbon
approach as M2's `RibbonPiece`): straight/start, 90° curve, ramp up/down, loop,
corkscrew — all built at run time.

The loop and corkscrew fit a single 8 m cell: the loop is a vertical circle that
also advances S→N (entering and exiting at ground level on opposite edges), and
the corkscrew is one barrel roll across the cell.

### 4. Editor built in code

`EditorController` builds the world and the entire UI in `_ready` rather than
hand-authoring `Editor.tscn`. This sidesteps the fragile parts of hand-written
scenes (Control layout, and the node-export-by-NodePath gotcha from ADR notes)
and keeps everything verifiable headlessly. Placement uses `_unhandled_input` so
clicks consumed by UI never leak into the world. Feedback is green/yellow/red per
`PlacementValidator`. **Test Drive** stashes the grid on the `GameState` autoload
and switches to `TrackPlay`, which rebuilds it into a drivable world and spawns
the car on the Start tile; Esc returns. The grid lives on `GameState`, so it
survives the editor↔play round trip.
